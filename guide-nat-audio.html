Diagnosing NAT One-Way Audio in SIP Calls

One of the most common — and most confusing — VoIP symptoms is a call that connects cleanly (SIP signaling completes, both phones show "connected") but audio only flows in one direction. This guide explains the usual cause and how to spot it in a log.

Signaling and Media Are Separate Paths

SIP itself only negotiates a call; it does not carry the audio. Once signaling completes, audio flows over a separate protocol, RTP (Real-time Transport Protocol), using IP addresses and ports that were negotiated inside the SDP (Session Description Protocol) body of the INVITE and its response. This separation is exactly why a call can "connect" while audio still fails — the two paths can succeed or fail independently.

The Classic NAT Problem

A phone or softphone sitting behind a NAT router often has no idea what its actual public IP address is. If it advertises its private LAN address in the SDP c= (connection) line and m=audio (media) line, the far end will try to send RTP packets to that private, unroutable address — packets that never arrive. The result: the side behind the misconfigured NAT never hears audio, while the other side (whose media address was advertised correctly) does.

What to Look For in the Log

  • Compare the SDP c=IN IP4 address against the actual source IP of the SIP packet (the Via header or transport-layer source). A private RFC 1918 address (10.x, 172.16–31.x, 192.168.x) in the SDP when the signaling clearly crossed the public internet is the classic tell.
  • Check whether the m=audio port matches what the far end is actually sending to — a media/RTP capture or the device's own logs will show the port it's transmitting on.
  • Confirm both the offer (in the INVITE) and the answer (in the 200 OK) — a one-way NAT issue can be on either leg of the call.

Typical Fixes

Common remedies include enabling SIP ALG carefully (it can also cause problems if misconfigured), deploying an SBC or media relay that rewrites SDP to the correct public address, using STUN so the endpoint learns its public IP/port, or forcing symmetric RTP so the media server replies to whatever source port it actually receives traffic from rather than trusting the SDP-advertised port.

Spotting It Faster

When you load a log into the SIP Log Analyzer, each INVITE and 200 OK in the sequence diagram shows its negotiated codec and media port directly on the flow arrow, so a mismatched or private-range media address is visible at a glance without manually digging through the SDP body of every message.
