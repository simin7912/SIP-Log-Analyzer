RFC 3261 Header Checklist for SIP Requests

RFC 3261 defines a small set of headers that must appear in every SIP request. A missing or malformed header here is one of the most common causes of interoperability failures between different vendors' equipment. This checklist covers the ones worth checking first, which is also what the analyzer's built-in compliance inspector flags automatically.

Mandatory Headers

  • Via — Records the path a request took so responses can be routed back the same way. Each proxy adds its own Via; a missing branch parameter breaks transaction matching.
  • To / From — Identify the logical parties in the dialog. The From header must carry a tag; the To tag is added by the callee in the first reliable response, not by the caller.
  • Call-ID — A globally unique identifier for the dialog, used to group every message belonging to one call.
  • CSeq — A sequence number plus method name, used to order transactions and match requests to responses.
  • Max-Forwards — A hop-limit counter (commonly starting at 70) that prevents infinite proxy loops. A request without it risks looping indefinitely on some proxies.
  • Contact — Required on INVITE and a small set of other requests; tells the far end the direct address to use for subsequent in-dialog requests, bypassing the original proxy chain where allowed.

Common Findings and What They Usually Mean

  • Missing Contact on INVITE — often causes mid-call requests (re-INVITE, BYE) to route back through the original proxy path instead of directly, or to fail outright on strict implementations.
  • Missing or zero Max-Forwards — usually a sign of a non-compliant client library rather than a real routing issue, but worth flagging before it causes a loop in a more complex proxy topology.
  • No provisional response before the final response — not itself an RFC violation, but on slower networks it often correlates with retransmissions, since the sender has no early confirmation the request was received.

Using This With the Analyzer
